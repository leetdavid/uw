# The theme's light or dark rides in Chromium's color key

On 2026-10-25 the user asked for the sidebar's theme and Chromium's look to be fully apart: "the cleaner implementation would be to completely separate the sidebar theming from the chromium theming", so that a light sidebar can sit beside dark pages, dark Settings, and dark menus. Chromium works out every color of a window from one color key, whose light or dark was the theme's. We decided that the key's light or dark is the [page mode](../plans/themes.md#page-mode), and that the theme's key rides in the key's slot for extra mixers, which uw already used for page colors. Those mixers give the sidebar, the edge around the page card, and uw's cards the colors the theme's own key gives them.

Chromium keeps colors by key, so two windows with the same page mode and different themes need different keys: the key is the only place the theme's mode can live. Every Chromium menu, bubble, dialog, and page then follows page mode with no work per surface. The sidebar's colors are Chromium's header, frame, and tab colors, picked by name, so new ones come along; a view in the sidebar that uses one of Chromium's general colors shows page mode instead, which a test that compares the sidebar's pixels catches. The menus and cards that open from the sidebar ask for the theme's mode themselves. A field of uw's own in `ui/color/color_provider_key.h` would have done the same, but would rebuild nearly all of Chromium and need carrying at each update.

Considered options: keeping the window on the theme's mode and pushing page mode onto each Chromium surface (rejected: every bubble, menu, dialog, and panel in the window needs its own hook, and each one missed stays in the wrong mode, as Settings and the extensions menu did after T191).
