# uw signs in with a client file on uwbrowser.com when a server can't register it

On 2026-10-28 the user's Home Assistant [connector](../CONTEXT.md#language) could not sign in. Its sign-in server lets no app register itself; it only takes a Client ID Metadata Document, where the client ID is the address of a JSON file that lists the app's return addresses. uw publishes that file at `https://uwbrowser.com/oauth/client.json` and uses its address as the client ID, but only when a server takes such files and offers no registration. Every other server still registers uw as before.

Builds carry the address, and servers cache the file, so it can never move. Anyone who controls uwbrowser.com or its Vercel project can change the file's return addresses and phish sign-ins in uw's name, so both accounts need strong protection. The user's server fetches the file at each sign-in, so uwbrowser.com sees that server's address. The file is public: any program can use uw's client ID, and a server could block it if one misuses it. Keeping the file as a last resort means a block, or uwbrowser.com being down, touches only servers that could not sign in any other way.

Considered options: the file whenever a server takes it, as MCP's spec suggests (rejected: Linear, Notion, Sentry, and the rest would depend on uwbrowser.com and share one client ID for no gain). `http://127.0.0.1:47651/` as the client ID, which Home Assistant accepts because it shares a host with the return address (rejected: Home Assistant's own rule; servers that follow the spec fetch the client ID over `https`).
