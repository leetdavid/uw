# Local builds are uw dev, a separate app from the installed uw

A local build and the installed preview shared the app ID `com.uwbrowser.uw` and the `uw-ai` Keychain items. macOS keys permissions and the default browser on the app ID, so on 2026-11-02 the screen-recording permission was tied to a local build and screen sharing failed in the installed uw. The installed uw also asked for the login password at every start for items a local build had saved. We chose to make every local build uw dev: app ID `com.uwbrowser.uw.dev`, the name "uw dev", the `uw-dev` profile folder, the `uw-ai-dev` Keychain service, and the `uw-dev` command. Only `pnpm run release` builds the installed uw, with the GN argument `uw_release`.

Considered options: a flag that turns uw dev on (rejected: a build without it clashes again), a second output folder for uw dev (rejected: twice the build time and disk), and rewriting a release's Info.plist files to the real identity when it is signed, as Chrome does for Canary (rejected: more files to rewrite, and the Keychain service is compiled in).

Consequences: uw dev asks for macOS permissions of its own, and asks again when its ad-hoc signature changes. The first time uw dev starts with no keys of its own, it copies the installed uw's model keys, one password prompt each. It does not copy connector sign-ins, since two apps refreshing one token can sign each other out. The release worktree's unsigned build carries the real app ID, so the release command makes macOS forget it after copying it out. The Mac only: Windows builds keep their install identity.
